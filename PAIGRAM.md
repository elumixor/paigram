# Paigram

Telegram for iOS with pai built into the bot's chat. The chat with the pai bot is a normal Telegram chat, so its messages forward, search and quote like any other, with these differences: it opens on pai's own topic and the topic strip is gone; its title is a breadcrumb ("pai › Hiring › Screener") that opens the topic list; and the bot's messages render their tool use the way Claude does, one grey line above the answer ("Ran 3 commands, read a file") that expands into a timeline, with the status card showing the current tool and elapsed time while a turn runs.

Where Telegram puts the avatar, the bot's chat shows a ring for the Claude limit that runs out first (held: every limit and what the sessions cost) and a phone that calls the topic's agent; a tap on the ring opens the topic's agent's profile (`openPaiProfile`).

Threads are the bot's Telegram topics. Dictation runs English, Russian and Ukrainian recognizers on the device at once and keeps the most confident transcript.

Code: `submodules/PaiUI` (the store, the profile lists, the settings screen, the trailer parser), `submodules/TelegramUI/Components/Chat/ChatMessagePaiToolsBubbleContentNode` (the tools node), `TelegramUI/Sources/Chat/ChatControllerPai.swift` (going between agents' topics, the topic list, profiles, forwarding pai's log), and small hooks in `ChatMessageBubbleItemNode`, `ChatMessageTextBubbleContentNode`, `ChatTextInputPanelNode`, `ChatControllerNode`, `ChatController` and `ChatControllerLoadDisplayNode`, `ChatInterfaceStateNavigationButtons` and `ChatControllerNavigationButtonAction`, all keyed on `PaiChat.isBot`. The bot's metadata rides in each message's trailing link (`pai/src/protocol/rich.ts`); pai-telegram fills in the tools, state and timings.

An ask whose options carry details (`optionDetails`, or per-question `details`: a picture, a line, a page) draws them as rows under the question (`PaiAsk`, `ChatMessagePaiAskBubbleContentNode`) in place of its option buttons; a tap sends the button's own callback, the page's domain opens the in-app browser, and the `• label — subtitle` list pai adds for plain clients is cut from the text. Done, Skip and link buttons stay. Record references (`keep:page/…`, `balance:block/…`, `git:repo@sha`, `#18`…) render as one pill each (`PaiPill`): mark, title, meta and status, resolved through the daemon's `/urn/resolve` and `/keep/preview` and cached a minute.

## Agents

Every agent of pai's but pai itself talks in its own forum topic of the bot's chat (pai's `agents.thread_id`, `threadId` in `/agents`); pai is the main topic. What the user types to an agent on the web or in the CLI comes back into its topic as the bot's messages with a `user` trailer, which `Message.isPaiEcho` (TelegramCore) draws as his own. A card, the rail or a thread link opens another agent's topic (`openPaiAgent`): going down the tree pushes it, going up pops back to it or switches this chat.

The breadcrumb opens Telegram's own forum topic list of the bot's chat, in the agent tree's order (pai first, then depth first, open agents before closed), each topic with its agent's portrait for an icon (`ChatListNodeLocation` re-indexes the topics, `ChatListItem` draws `PaiAgentList.topicIcon`); a topic that is no agent's follows them by its last message. The list goes under the chat, which pops off onto it, so a topic picked there opens above the list.

Each agent is also a local `TelegramUser` (in the `Email` peer namespace, ids from `1 << 52` up, `PeerId.isPaiAgent`), in no chat list: only its identity, its portrait as its photo, for its profile. The app hands TelegramCore the agent list and the bot's peer (`PaiAgentPeers`, `TelegramEngine.PaiAgents.update`). The profile is Telegram's profile screen on that peer (`PeerInfoPaiItems.swift`): its role and what it is doing under its name, Call (pai's voice call, `PaiCall`), and rows for its role, status, job, its Keep page, the agents under it, and its tasks and routines (read-only lists, `PaiProfile.swift`); pai's own adds the calls, what the sessions are given (tools, skills, instructions, memories) and Settings (the daemon, the limits, signing out).

A topic begins when pai made it, but an agent older than topics said things before; those are only in pai's message log. TelegramCore gives each agent's topic a `Box` hole (`Sources/PaiAgents/PaiTopicHistory.swift`) that Postbox fills like any history as the topic is scrolled back to it: a page of `GET /messages?agent=&beforeAt=<topic created>`, stored as the bot's incoming messages in the topic, dated when written, with a trailer drawn as the bot draws its own (`result`, `user`, `event`, cards, asks, notices). Their ids are the row's id times 32 plus a slot per topic, so a hand-off row can be in both agents' topics. Such a message is no Telegram message: it cannot be replied to, reacted to, unsent or reported, deleting it deletes it on this device only, and its menu is Copy and Forward.

Forward in the bot's chat offers only his own messages and pai's and its agents' answers (`PaiChat.isForwardable`: no event, card, ask, notice or status line). A row of pai's log is first posted by the bot as real messages (`POST /telegram/materialize`, once per row), which are forwarded in its place (`materializePaiRows`).

## Email

Email reads as chats behind one "Email" row at the top of the chat list, which opens them by date in the chat list's inline stack (full width, tab bar kept), each with an envelope on the avatar's corner. They are a local peer group (`Namespaces.PeerGroup.email`) that Telegram's server never hears of, so the row counts unread by itself and its chats stay out of folder tabs; an archived email chat stays in the archive and goes back behind the row when unarchived. Every person the mailboxes correspond with is one chat: anyone the user has written to, and anyone Spark files under People (Gmail's Primary tab for senders Spark never saw), across all three mailboxes. The box's email connector (`email` connector (`desk-connectors`)) owns the mailboxes and their Google sign-ins; it keeps an index of every message's headers, follows Gmail through Pub/Sub, and gives the app `/gmail/contacts`, `/gmail/changes`, `/gmail/conversation` (a chat's history, a page at a time), `/gmail/search`, `/gmail/attachment`, `/gmail/send`, `/gmail/read`, `/gmail/trash` and `/gmail/mute`. New mail is pushed by pai itself (`POST /push/devices`, an APNs key on the box), not by Telegram.

In the app an email chat is a `TelegramUser` in its own peer namespace (`Namespaces.Peer.Email`, the box's contact id) whose messages live in `Namespaces.Message.Box`, with ids that follow the date (`BoxMessageIds`), so Postbox's history holes load older mail as the chat scrolls. TelegramCore's `Sources/Email/` holds the sync (on the shared box layer in `Sources/Box/`: the client, message ids, history holes, read states, outgoing messages) (the contact list, then the change log every half minute, on return to the app and on a push), the history holes, the read marks, the sends (stored as sending and settled by the box's answer, never through Telegram's pending messages) and the search, which asks Gmail after the local text index. A message's text comes from the box already drawn: bold, italics and links behind words as entities, with stylesheets, hidden preview text and logos gone; links in an email chat open without Telegram's confirmation. Raising `EmailState.currentTextVersion` refetches every stored email the next time the app syncs, for when the box changes how it draws text. Nothing about a box chat reaches Telegram's servers: `forceApiInputPeer` and `apiInputPeer` refuse it, and the read-state, notification-settings, pinned-chat and reset paths branch on `PeerId.isBridged`. The app side (`submodules/PaiUI/Sources/Mail`) points TelegramCore at the box, registers for pushes, shows the address under the chat's title, and is Settings › Email: the mailboxes as Spark names them, and a chat with a new address.

Sending from a chat replies to everyone in the latest thread with that person, from the mailbox the thread is in and as the address it was written to (ATMA answers as ceo@atmagaming.com, a send-as alias of ceo.atmagaming@gmail.com); a reply to a bubble answers that email; a first message starts a thread whose subject is its first line. Reading marks mail read in Gmail and deleting moves it to the Trash, so Spark sees the same mailbox. `bun run import-spark` in `email` connector (`desk-connectors`) sends Spark's account names, colours, its People sorting and its cached pictures to the box.

Every email chat has a picture: the box resolves the photo Google contacts have for the address, else its Gravatar, else the company's logo, and the app shows it as the peer's photo from `/gmail/avatar?v=<hash>`. Every incoming mail arrives summarised (a person's short note excepted), written as the content itself, never "X says that…". The box answers a page at once with what it has and writes summaries and answers behind it (`pending` on a message); the finished message comes through the change log, which the app reads again a few seconds after a page with pending mail. its bubble is the box's one-or-two-sentence summary over a link-preview card (sender, subject, the picture a machine's mail picked), and the card, or "View Original" in any email's menu, opens the whole email as its sender made it in the app's own browser. Which mail a machine sent is the box's call in any language. A push carries the summary's one-line version and the picture; all mail is one stack in Notification Center, each sender a conversation with its photo. The notification extension reads the box's address and this phone's token from `pai.json` in the app group, which the app writes at launch and on sign-in.

When a chat's latest mail asks something, the box offers answers for it (kept per chat, written again when a new message lands) and they show as buttons under that bubble (`ReplyMarkupMessageAttribute`, callback data `email-reply:<label>`): a tap makes the email the reply target, puts the label in the composer and runs ✨ compose on it, so the reply is drafted in his voice and never sent by itself; any newer message takes the buttons away. A mail that asks him to do something through a link (register, pay, confirm) also gets up to two link buttons (`actions`) above the answers; those stay on their mail. A mail with a `List-Unsubscribe` header gets an Unsubscribe button between them and the answers: the box does it (`/gmail/unsubscribe`: the one-click POST, else the email the header asks for) and the button goes, or, when the header names only a page, the button opens it. An email's files and its text are one bubble: a group of file messages with the text under the last one; a summary's card stays its own bubble above the files.

Settings › Email lists the mailboxes; "Add Mailbox…" asks for a short name and opens Google's consent, "New Email…" opens a screen for an address, name, mailbox and subject. A `mailto:` link (the app registers the scheme) opens an email chat with that address, subject and body carried over. Being the default mail app needs Apple's `com.apple.developer.mail-client`, requested 2026-11-03.

## WhatsApp

His own WhatsApp reads as chats too, with a WhatsApp mark on the avatar's corner. Settings › WhatsApp shows whether the box is linked, links it from this phone with a pairing code (WhatsApp's "Link with phone number"), links it again, turns the box's pushes off and reloads the chats. The box's WhatsApp connector (`whatsapp` connector (`desk-connectors`), linked to his number by QR) keeps every chat, person and message it sees and asks his phone for older history as a chat scrolls; the app gets `/whatsapp/chats`, `/whatsapp/changes`, `/whatsapp/conversation`, `/whatsapp/search`, `/whatsapp/media`, `/whatsapp/avatar`, `/whatsapp/send`, `/whatsapp/read` and `/whatsapp/mute`. A person is a `TelegramUser` in `Namespaces.Peer.WhatsApp` (the box's person id), the same peer whether it is a DM or an author in a group; a group is a `TelegramGroup` in `Namespaces.Peer.WhatsAppGroup`. `Sources/WhatsApp/` mirrors the email side on the box layer: photos, videos, voice messages, files and stickers are fetched from the box when shown, WhatsApp's markup becomes entities, a reply quotes its message, and sends (text, or a file as a form) are read back by the box before they count. WhatsApp's archive is the archive here; muting and reading here mute and read on WhatsApp.

## Stats

Settings › Stats reads the box for a day, a week or a month: AI spend by feature (compose, mail summaries, headlines, and Claude's own sessions) from `/spend`, mail in, out, opened, summarised and pushed from `/gmail/stats`, and WhatsApp traffic from `/whatsapp/stats`.

## Compose

The ✨ button in the composer rewrites the draft through the box's `/compose` (Sonnet): the message in the chat's language and in his own way of writing to this person, every fact kept and nothing added; when the draft leaves something open it asks first. Long-press keeps Telegram's own AI editor.

## Launch

Every list the app shows (sessions, tasks, projects, agents, needs, usage) is cached as JSON in `Caches/pai` (`PaiCache`), read and decoded off the main thread, and shown before the network answers; `PaiChat.preload()` starts those reads at configure. The first fetch after start skips the 300 ms debounce, later event bursts keep it. The session list publishes as soon as tasks and projects arrive; the slower `/threads/all` merges in afterwards. A usage reading with no windows keeps the last known windows until they reset (app, widget and watch). `PaiPerf` logs `PAIPERF <name> +<ms since process start>` at each launch step: `log stream --predicate 'eventMessage CONTAINS "PAIPERF"'`.

## Usage glance, widget and watch

One snapshot, the glance (`submodules/PaiGlance`), feeds every surface outside the app: today's spend, the plan's Session and Weekly windows, spend by agent, how many threads run, and the questions waiting on him. `PaiGlanceLiveSource` reads the box's `/usage/summary` and `/needs` together (falling back to `/spend/forecast`, `/spend`, `/needs`, `/rail` and `/agents` on a box without the summary). `PaiGlanceSync` (`submodules/PaiUI`) refreshes it while the app runs and writes it to the app group, where the home-screen widget (`Telegram/WidgetKitWidget/PaiUsageWidget.swift`, small and medium) reads it; a tap opens `paigram://usage` or `paigram://agent/<slug>`, the agent's chat.

Crossing 50, 80 or 100% of a window posts a local alert (`PaiUsageAlerts`); the box sends the same crossing as a push (`paiUsage` in its data, thread `pai.usage`, collapse id the same as the alert id below). Both use the id `pai.usage.<window>.<threshold>.<reset>`: the notification extension removes the local alert when the push lands, and the app skips an alert a delivered push already told. Tapping either opens the usage screen.

The watch gets the box's address, token and latest glance from the phone over WatchConnectivity and keeps them in its keychain group (`PaiVault`), so it reads the box on its own when the phone is away. Its Pai screen shows the glance and lists the questions with their options, answered straight to the box (through the phone when the box is out of reach); the box's ask pushes and their action buttons still mirror to the wrist. The `PaiComplications` widget extension (`<watch id>.widget`) draws the window that runs out first as a gauge, with spend and waiting questions in the larger families, and is signed with `WatchWidget.mobileprovision` (`scripts/provision.ts`); without that profile the build drops the extension.

## Build

Bazel builds, driven by Telegram's `build-system/Make/Make.py`. First time: `bun install`, then copy `build-system/paigram.example.json` to `build-system/paigram.json` and `build-system/paigram-sim.json` (api id and hash from my.telegram.org; the simulator file keeps the bundle id `ph.telegra.Telegraph`, which the repo's fake codesigning profiles are bound to). Every build writes `submodules/PaiUI/Sources/PaiSecrets.swift` from `~/.config/pai/box.json` and the box's `/m/telegram/info`, so the app ships with its server and bot name (no credential: each phone signs in to pai and keeps its own device token in the keychain, `PaiAuth`); where there is no box file (CI) `PAI_BOX_URL` and `PAI_BOT_USERNAME` stand in for it.

```sh
bun run sim [--no-build]          # simulator build, installed and launched on the newest iPhone simulator
bun run device [--no-build] [--device <name>]   # the release build signed Ad Hoc, installed and launched on a paired iPhone over USB or Wi-Fi
bun run ci-secrets                # once, on the Mac: fill the GitHub secrets CI needs from the box and the keychain
bun run tag [--minor]             # bump the version, tag it `ios-vX.Y.Z` and push; builds nothing until pai's build card dispatches TestFlight on that tag
bun run precheck                  # type-check Paigram's widget and watch Swift against the SDKs in seconds; the release scripts run it first
bun run testflight [--no-build] [--no-bump] [--minor]   # the same release from a Mac, locally: version bump, App Store profile via the API, release build, upload, wait
bun run typecheck                 # the scripts
```

TestFlight needs `.env` with `ASC_KEY_ID`, `ASC_ISSUER_ID`, `TEAM_ID` and the key at `~/.appstoreconnect/private_keys/`. The TestFlight build ships everything the official app does: the share, notification service and content, Siri intents, widget and broadcast upload extensions, and the watch app (`Telegram/WatchApp`, built by xcodebuild and embedded with `--embedWatchApp`). `scripts/provision.ts` registers the bundle id of each with its capabilities and writes a fresh App Store profile for every one. The App Store Connect app record and the app group `group.com.elumixor.paigram` have to be created by hand in the portal, and the group attached to each extension's bundle id there, which the API does not allow; provisioning checks the profiles and says which ids still lack it. The same goes for Communication Notifications on the app's own id, which lets a notification carry the sender's photo with the app icon in its corner: tick it on the id in the portal, and provisioning refuses to go on while the profile lacks it. Simulator builds leave the extensions out unless `bun run sim --extensions`.

Day to day the app goes on the phone with `bun run device`, not TestFlight: the same release build with the extensions (the watch app left out), signed with the Distribution certificate under Ad Hoc profiles, so push stays on production APNs, then `devicectl` installs it over the TestFlight copy and keeps its data. No upload, no processing wait, no version bump. The iPhone has to be paired with the Mac once by cable: `xcrun devicectl manage pair --device <udid>` (Trust on the phone, Developer Mode on), and for Wi-Fi `uvx pymobiledevice3 lockdown set True com.apple.mobile.wireless_lockdown EnableWifiDebugging` (Xcode's Connect via network). After that it installs over Wi-Fi while awake on the Mac's network, in under a minute. A new iPhone is registered on the account and the Ad Hoc profiles (`build-input/paigram-codesigning-adhoc/`) are made again to include it. TestFlight is for releases.

The icon is `Telegram/Telegram-iOS/Telegram.icon` (Icon Composer: a P in a dashed chat bubble, black on white, white on black in dark mode; source `docs/brand/paigram.svg`). Its layer is outlined to filled paths: Icon Composer fills a stroked path's whole shape. The watch app takes a flat PNG instead, `Telegram/Telegram-iOS/WatchAppIcon.png`, which replaces the snapshot's Telegram icon at build time; after changing the icon, `bun run watch-icon` renders it again from the `.icon` (needs ImageMagick).

Upstream pins Xcode 26.2; `--overrideXcodeVersion` lets the installed Xcode build it. Bazel is downloaded to `build-input/` on first run; the disk cache lives in `~/telegram-bazel-cache`.

### Releasing

Neither TestFlight workflow runs by itself: both are `workflow_dispatch` only. A build ready for the owner is offered with `offer_build` (pai's build card), never by tagging a release or asking him to open dev. The card's TestFlight action runs `gh workflow run testflight.yml --ref ios-vX.Y.Z`, so a release first needs its tag: `bun run tag` bumps `versions.json`, commits, tags `ios-vX.Y.Z` and pushes, and starts no build. The workflow builds with `--no-bump --once`, so dispatching on a version already on TestFlight uploads nothing; cut a new tag for a new build. When the Mac's run fails, its `fallback` job dispatches the GitHub runner's workflow on the same tag.

| Workflow | Runs on | A warm build | Fails when |
| --- | --- | --- | --- |
| `testflight.yml` (TestFlight) | the developer's Mac, a self-hosted runner labelled `paigram-mac` | 15–40 min from the Bazel cache in `~/telegram-bazel-cache` (0.2.5: 47 min; the 0.4.0 build itself 11 min) | the Mac sleeps mid-build (GitHub fails the job ten minutes after the runner goes quiet); the synced tree is not the tagged commit |
| `testflight-hosted.yml` (TestFlight (GitHub runner)) | a GitHub `macos-26` runner, free for this public repo | 1h30–1h40 end to end: up to 40 min queue, 50–60 min build from the restored cache, 10 min processing (0.3.2 and 0.4.0 shipped this way) | GitHub's macOS pool has no machine: the job sits 15 min, then ends with "not acquired by Runner of type hosted"; a compile error Bazel reaches after 50 min |

**On the Mac.** The workflow runs `scripts/mac-release.ts` in `~/dev/@desk/native/paigram-ios`, the tree the box syncs to the Mac, not a second checkout (the disk has no room for one). It fetches the tag (force, so a moved tag replaces the Mac's copy), checks that the synced files are exactly the tagged commit by reading the tag's tree into a scratch index (the Mac's own `.git` lags behind the synced files, so its index would call every newer file deleted), trims the Bazel cache to 25 GB, then runs `bun run testflight --no-bump --once` under `caffeinate -ims`, which keeps the Mac awake on AC power; on battery with the lid closed it sleeps anyway. Signing and the App Store Connect key are the Mac's own. That tree is a one-way replica of the box (Mutagen, set up by dev): any file a build writes into it is put back to the box's copy within a second, unless its path is ignored by the sync. So everything the build generates sits under `build-input/`, which dev's mirror ignores (`BUILD_OUTPUT` in dev's `cli/files.ts`): Bazel itself, the configuration repository `Make.py` writes with the profiles it signs with, and the fresh profiles from `scripts/provision.ts` (`build-input/paigram-codesigning/`). Before that, the 0.4.0 and 0.4.1 Mac builds signed with the box's stale Ad Hoc profiles and App Store Connect refused the upload (error 90046 on the watch app's `application-identifier`); The watch app is signed by its own Bazel action, which gets the profile as a path rather than an input, so `Make.py` also passes a digest of the watch profiles (`--define=watchProvisioningProfileDigest`): without it Bazel kept serving the watch app signed with an earlier profile. `bun run testflight` compares the watch app's embedded profile with its bundle id before uploading. When the job ends with anything but success (a failed check, a build error, a lost runner, the 150-minute timeout) the workflow's `fallback` job dispatches the GitHub runner's workflow for the same tag. On success it cancels any GitHub runner build of the tag still in flight.

The runner is `~/.local/share/actions-runner/paigram/`, a LaunchAgent (`~/Library/LaunchAgents/actions.runner.elumixor-paigram.Vs-MacBook-Air.plist`, `RunAtLoad` and `KeepAlive` on, so it comes back after sleep, a crash or a self-update); logs in `~/Library/Logs/actions.runner.elumixor-paigram.Vs-MacBook-Air/` and `_diag/` under the runner. A job queued while the Mac sleeps waits in GitHub's queue and runs when the runner reconnects; it is not lost. `bun run tag` asks GitHub whether the runner is online before tagging and warns when it is not, since the release then depends on the GitHub runner alone. To reinstall: Settings → Actions → Runners → New self-hosted runner, `./config.sh --labels paigram-mac`, `./svc.sh install && ./svc.sh start`.

**On the GitHub runner.** It runs only when dispatched, by the Mac's `fallback` or by hand. The build itself is the reusable `testflight-hosted-build.yml`, called with `runner: macos-26`; when that job never reached a machine (the jobs API shows no runner name and no steps) `retry-check` calls it again with `macos-15`, whose image has the same Xcode 26 and a shorter queue. A build that failed on its own is not retried. The retry job's condition starts with `always()`: without it GitHub skips the job because `build`, further up its chain, did not succeed. Run from the Actions tab on a branch rather than a tag, it builds whatever `versions.json` says and takes the next free build number.

The hosted steps are thin over the same scripts a Mac runs: `scripts/ci.ts` prepares the runner, `bun run precheck` type-checks Paigram's own Swift, then `bun run testflight --no-bump --once` provisions, builds, uploads and waits. `scripts/ci.ts` is everything a developer's Mac already has and a bare runner does not: it checks every secret up front — a missing one fails in seconds rather than an hour into Bazel — writes the App Store Connect key to `~/.appstoreconnect/private_keys/`, writes `build-system/paigram.json` from the committed example, and imports the distribution certificate into a throwaway keychain with a partition list so `codesign` never waits for a prompt. It also refuses a tag whose version does not match `versions.json`. `scripts/trim-cache.ts` trims the Bazel disk cache to 8 GB, least recently used first, before `actions/cache` saves it, because GitHub rejects an entry over 10 GB; the cache is saved even when the build fails, so the next attempt starts from the work that did get through. The runner is cleaned first — every Xcode but the selected one and all simulator runtimes go — since GitHub's macOS runners have only 14 GB free and this build plus its cache does not fit beside them.

**Precheck.** `bun run precheck` (`scripts/precheck.ts`) type-checks with `swiftc` the Paigram Swift of the two targets with the oldest deployment floors: `submodules/PaiGlance` and the widget against the iOS 15 SDK, the watch app's `PaiComplications` and `PaiShared` against watchOS 26. It takes three seconds and catches what cost the 0.4.1 hosted build 50 minutes (a `WidgetFamily` case that is iOS 16 only). `bun run testflight` and `bun run device` run it before provisioning, the hosted workflow before restoring the cache.

**What else was weighed.** A queue on the box that waits for the Mac and builds through the dev agent adds nothing: GitHub's queue already holds the job while the Mac sleeps, and the hosted twin covers the gap. Paid larger runners (`macos-26-xlarge`, more cores) would shorten the build and the queue at a per-minute price, with the same capacity failures reported for the free pool; worth it only if the free pool keeps refusing jobs. A Bazel remote cache would let the hosted runner start warm without the 8 GB `actions/cache` round trip, at the cost of running and paying for a cache server.

Once, from the Mac that holds the Apple material:

```sh
bun run ci-secrets [--p12 <path>]
```

`scripts/ci-secrets.ts` sets all ten repo secrets itself. Seven of the values already live on the box and it reads them over `pai ssh` (the `.env`, `build-system/paigram.json` and `~/pai/data/config.json` there, plus the box's own `/m/telegram/info` for the bot name); the App Store Connect key and the distribution certificate exist nowhere but that Mac, so it reads the key out of `~/.appstoreconnect/private_keys/` and exports the certificate from the login keychain — macOS asks for the login password before it releases a private key, and if more than one distribution identity is in there it asks which one. `security export` cannot be pointed at a single identity, so it exports the keychain's identities and separates the chosen certificate and its key out with openssl; `--p12 <path>` skips all of that and takes a `.p12` exported by hand from Keychain Access instead. Every value goes to `gh secret set` on stdin, so none of them reaches argv or shell history. It needs `gh` logged in with access to the repo, and checks that before it reads anything.

The secrets it sets, for setting them by hand under Settings → Secrets and variables → Actions:

| Secret | What |
| --- | --- |
| `ASC_KEY_ID` | App Store Connect API key id |
| `ASC_ISSUER_ID` | App Store Connect issuer id |
| `ASC_KEY_P8` | base64 of `AuthKey_<id>.p8` (`base64 -i AuthKey_<id>.p8`) |
| `TEAM_ID` | Apple Developer team id |
| `DIST_CERT_P12` | base64 of the Apple Distribution certificate **with its private key** — the same certificate `scripts/provision.ts` picks, which is the newest unexpired one on the account |
| `DIST_CERT_P12_PASSWORD` | the password that `.p12` was exported with |
| `TELEGRAM_API_ID` | `api_id` from my.telegram.org |
| `TELEGRAM_API_HASH` | `api_hash` from my.telegram.org |
| `PAI_BOX_URL` | the box the app talks to |
| `PAI_BOT_USERNAME` | the box's bot username, without the `@` (set so the build does not have to reach the box) |

`.github/workflows/build.yml` is upstream Telegram's CI — a full Bazel build with fake codesigning, producing an unsigned ipa on a GitHub release. It no longer runs on pushes to master: macOS runners bill at ten times the Linux rate and that ipa is of no use here, so it is `workflow_dispatch` only and no push starts any build.
