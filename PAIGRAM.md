# Paigram

Telegram for iOS with pai built into the bot's chat. The chat with the pai bot is a normal Telegram chat, so its messages forward, search and quote like any other, with three differences: the topic strip is gone and the chat opens on the thread it was on last time; the bot's "Menu" button is a Pai button (a dot on it means a thread is running or waiting) that opens the Pai screen, threads grouped by project with a composer that starts a new one from text or dictation; and the bot's messages render their tool use the way Claude does, one grey line above the answer ("Ran 3 commands, read a file") that expands into a timeline, with the status card showing the current tool and elapsed time while a turn runs.

The bot's avatar in the chat's bar (where Telegram would put the topics menu) opens the Pai settings instead of a profile: threads running, uptime, the Claude limits and what the sessions cost, and what the sessions are given — tools by MCP server, skills, the instructions in their parts, memories — read from the daemon's `/context`, `/usage` and `/health`.

Picking a thread on the Pai screen returns to the chat on that topic. Threads are the bot's Telegram topics; the Pai screen reads their state from the pai daemon (`/tasks`, `/task`, `/m/telegram/info`) and follows `/events`. Dictation runs English, Russian and Ukrainian recognizers on the device at once and keeps the most confident transcript.

Code: `submodules/PaiUI` (the store, the Pai screen, the settings screen, the trailer parser), `submodules/TelegramUI/Components/Chat/ChatMessagePaiToolsBubbleContentNode` (the tools node), and small hooks in `ChatMessageBubbleItemNode`, `ChatMessageTextBubbleContentNode`, `ChatTextInputPanelNode`, `ChatControllerNode`, `ChatController` and `ChatControllerLoadDisplayNode`, `ChatInterfaceStateNavigationButtons` and `ChatControllerNavigationButtonAction`, all keyed on `PaiChat.isBot`. The bot's metadata rides in each message's trailing link (`pai/src/protocol/rich.ts`); pai-telegram fills in the tools, state and timings.

## Email

Email reads as chats, mixed into the chat list by date with an envelope on the avatar's corner. Every person the mailboxes correspond with is one chat: anyone the user has written to, and anyone Spark files under People (Gmail's Primary tab for senders Spark never saw), across all three mailboxes. The box's email connector (`email` connector (`desk-connectors`)) owns the mailboxes and their Google sign-ins; it keeps an index of every message's headers, follows Gmail through Pub/Sub, and gives the app `/gmail/contacts`, `/gmail/changes`, `/gmail/conversation` (a chat's history, a page at a time), `/gmail/search`, `/gmail/attachment`, `/gmail/send`, `/gmail/read`, `/gmail/trash` and `/gmail/mute`. New mail is pushed by pai itself (`POST /push/devices`, an APNs key on the box), not by Telegram.

In the app an email chat is a `TelegramUser` in its own peer namespace (`Namespaces.Peer.Email`, the box's contact id) whose messages live in `Namespaces.Message.Box`, with ids that follow the date (`BoxMessageIds`), so Postbox's history holes load older mail as the chat scrolls. TelegramCore's `Sources/Email/` holds the sync (on the shared box layer in `Sources/Box/`: the client, message ids, history holes, read states, outgoing messages) (the contact list, then the change log every half minute, on return to the app and on a push), the history holes, the read marks, the sends (stored as sending and settled by the box's answer, never through Telegram's pending messages) and the search, which asks Gmail after the local text index. A message's text comes from the box already drawn: bold, italics and links behind words as entities, with stylesheets, hidden preview text and logos gone; links in an email chat open without Telegram's confirmation. Raising `EmailState.currentTextVersion` refetches every stored email the next time the app syncs, for when the box changes how it draws text. Nothing about a box chat reaches Telegram's servers: `forceApiInputPeer` and `apiInputPeer` refuse it, and the read-state, notification-settings, pinned-chat and reset paths branch on `PeerId.isBridged`. The app side (`submodules/PaiUI/Sources/Mail`) points TelegramCore at the box, registers for pushes, shows the address under the chat's title, and is Settings › Email: the mailboxes as Spark names them, and a chat with a new address.

Sending from a chat replies to everyone in the latest thread with that person, from the mailbox the thread is in and as the address it was written to (ATMA answers as ceo@atmagaming.com, a send-as alias of ceo.atmagaming@gmail.com); a reply to a bubble answers that email; a first message starts a thread whose subject is its first line. Reading marks mail read in Gmail and deleting moves it to the Trash, so Spark sees the same mailbox. `bun run import-spark` in `email` connector (`desk-connectors`) sends Spark's account names, colours, its People sorting and its cached pictures to the box.

Every email chat has a picture: the box resolves the photo Google contacts have for the address, else its Gravatar, else the company's logo, and the app shows it as the peer's photo from `/gmail/avatar?v=<hash>`. Every incoming mail arrives summarised (a person's short note excepted), written as the content itself, never "X says that…". The box answers a page at once with what it has and writes summaries and answers behind it (`pending` on a message); the finished message comes through the change log, which the app reads again a few seconds after a page with pending mail. its bubble is the box's one-or-two-sentence summary over a link-preview card (sender, subject, the picture a machine's mail picked), and the card, or "View Original" in any email's menu, opens the whole email as its sender made it in the app's own browser. Which mail a machine sent is the box's call in any language. A push carries the summary's one-line version and the picture; all mail is one stack in Notification Center, each sender a conversation with its photo. The notification extension reads the box's address and this phone's token from `pai.json` in the app group, which the app writes at launch and on sign-in.

When a chat's latest mail asks something, the box offers answers for it (kept per chat, written again when a new message lands) and they show as buttons under that bubble (`ReplyMarkupMessageAttribute`, callback data `email-reply:<label>`): a tap makes the email the reply target, puts the label in the composer and runs ✨ compose on it, so the reply is drafted in his voice and never sent by itself; any newer message takes the buttons away. A mail that asks him to do something through a link (register, pay, confirm) also gets up to two link buttons (`actions`) above the answers; those stay on their mail. An email's files and its text are one bubble: a group of file messages with the text under the last one; a summary's card stays its own bubble above the files.

Settings › Email lists the mailboxes; "Add Mailbox…" asks for a short name and opens Google's consent, "New Email…" opens a screen for an address, name, mailbox and subject. A `mailto:` link (the app registers the scheme) opens an email chat with that address, subject and body carried over. Being the default mail app needs Apple's `com.apple.developer.mail-client`, requested 2026-11-03.

## WhatsApp

His own WhatsApp reads as chats too, with a WhatsApp mark on the avatar's corner. Settings › WhatsApp shows whether the box is linked, links it from this phone with a pairing code (WhatsApp's "Link with phone number"), links it again, turns the box's pushes off and reloads the chats. The box's WhatsApp connector (`whatsapp` connector (`desk-connectors`), linked to his number by QR) keeps every chat, person and message it sees and asks his phone for older history as a chat scrolls; the app gets `/whatsapp/chats`, `/whatsapp/changes`, `/whatsapp/conversation`, `/whatsapp/search`, `/whatsapp/media`, `/whatsapp/avatar`, `/whatsapp/send`, `/whatsapp/read` and `/whatsapp/mute`. A person is a `TelegramUser` in `Namespaces.Peer.WhatsApp` (the box's person id), the same peer whether it is a DM or an author in a group; a group is a `TelegramGroup` in `Namespaces.Peer.WhatsAppGroup`. `Sources/WhatsApp/` mirrors the email side on the box layer: photos, videos, voice messages, files and stickers are fetched from the box when shown, WhatsApp's markup becomes entities, a reply quotes its message, and sends (text, or a file as a form) are read back by the box before they count. WhatsApp's archive is the archive here; muting and reading here mute and read on WhatsApp.

## Stats

Settings › Stats reads the box for a day, a week or a month: AI spend by feature (compose, mail summaries, headlines, and Claude's own sessions) from `/spend`, mail in, out, opened, summarised and pushed from `/gmail/stats`, and WhatsApp traffic from `/whatsapp/stats`.

## Compose

The ✨ button in the composer rewrites the draft through the box's `/compose` (Sonnet): the message in the chat's language and in his own way of writing to this person, every fact kept and nothing added; when the draft leaves something open it asks first. Long-press keeps Telegram's own AI editor.

## Build

Bazel builds, driven by Telegram's `build-system/Make/Make.py`. First time: `bun install`, then copy `build-system/paigram.example.json` to `build-system/paigram.json` and `build-system/paigram-sim.json` (api id and hash from my.telegram.org; the simulator file keeps the bundle id `ph.telegra.Telegraph`, which the repo's fake codesigning profiles are bound to). Every build writes `submodules/PaiUI/Sources/PaiSecrets.swift` from `~/.config/pai/box.json` and the box's `/m/telegram/info`, so the app ships with its server and bot name (no credential: each phone signs in to pai and keeps its own device token in the keychain, `PaiAuth`); where there is no box file (CI) `PAI_BOX_URL` and `PAI_BOT_USERNAME` stand in for it.

```sh
bun run sim [--no-build]          # simulator build, installed and launched on the newest iPhone simulator
bun run device [--no-build] [--device <name>]   # the release build signed Ad Hoc, installed and launched on a paired iPhone over USB or Wi-Fi
bun run ci-secrets                # once, on the Mac: fill the GitHub secrets CI needs from the box and the keychain
bun run tag [--minor]             # bump the version, tag it `ios-vX.Y.Z` and push: this Mac (self-hosted runner) builds and uploads to TestFlight
bun run testflight [--no-build] [--no-bump] [--minor]   # the same release from a Mac, locally: version bump, App Store profile via the API, release build, upload, wait
bun run typecheck                 # the scripts
```

TestFlight needs `.env` with `ASC_KEY_ID`, `ASC_ISSUER_ID`, `TEAM_ID` and the key at `~/.appstoreconnect/private_keys/`. The TestFlight build ships everything the official app does: the share, notification service and content, Siri intents, widget and broadcast upload extensions, and the watch app (`Telegram/WatchApp`, built by xcodebuild and embedded with `--embedWatchApp`). `scripts/provision.ts` registers the bundle id of each with its capabilities and writes a fresh App Store profile for every one. The App Store Connect app record and the app group `group.com.elumixor.paigram` have to be created by hand in the portal, and the group attached to each extension's bundle id there, which the API does not allow; provisioning checks the profiles and says which ids still lack it. The same goes for Communication Notifications on the app's own id, which lets a notification carry the sender's photo with the app icon in its corner: tick it on the id in the portal, and provisioning refuses to go on while the profile lacks it. Simulator builds leave the extensions out unless `bun run sim --extensions`.

Day to day the app goes on the phone with `bun run device`, not TestFlight: the same release build with the extensions (the watch app left out), signed with the Distribution certificate under Ad Hoc profiles, so push stays on production APNs, then `devicectl` installs it over the TestFlight copy and keeps its data. No upload, no processing wait, no version bump. The iPhone has to be paired with the Mac once by cable: `xcrun devicectl manage pair --device <udid>` (Trust on the phone, Developer Mode on), and for Wi-Fi `uvx pymobiledevice3 lockdown set True com.apple.mobile.wireless_lockdown EnableWifiDebugging` (Xcode's Connect via network). After that it installs over Wi-Fi while awake on the Mac's network, in under a minute. A new iPhone is registered on the account and the Ad Hoc profiles (`build-system/paigram-codesigning-adhoc/`) are made again to include it. TestFlight is for releases.

The icon is `Telegram/Telegram-iOS/Telegram.icon` (Icon Composer: a chat bubble in the shape of a p with a sparkle in its bowl, on a violet to blue gradient). The watch app takes a flat PNG instead, `Telegram/Telegram-iOS/WatchAppIcon.png`, which replaces the snapshot's Telegram icon at build time; after changing the icon, `bun run watch-icon` renders it again from the `.icon` (needs ImageMagick).

Upstream pins Xcode 26.2; `--overrideXcodeVersion` lets the installed Xcode build it. Bazel is downloaded to `build-input/` on first run; the disk cache lives in `~/telegram-bazel-cache`.

### Releasing from CI

`bun run tag` is the whole release and needs no Mac: it bumps `versions.json`, commits, tags `ios-vX.Y.Z` and pushes, and `.github/workflows/testflight.yml` does the rest on a GitHub macOS runner — a real signed release build with the extensions and the watch app, uploaded to TestFlight. The workflow is deliberately thin over the same scripts a Mac runs: `scripts/ci.ts` prepares the runner, then `bun run testflight --no-bump` provisions, builds, uploads and waits. It also runs from the Actions tab (`workflow_dispatch`), which builds whatever `versions.json` currently says and takes the next free build number from App Store Connect.

`scripts/ci.ts` is everything a developer's Mac already has and a bare runner does not: it checks every secret up front — a missing one fails in seconds rather than an hour into Bazel — writes the App Store Connect key to `~/.appstoreconnect/private_keys/`, writes `build-system/paigram.json` from the committed example, and imports the distribution certificate into a throwaway keychain with a partition list so `codesign` never waits for a prompt. It also refuses a tag whose version does not match `versions.json`. `scripts/trim-cache.ts` trims the Bazel disk cache to 8 GB, least recently used first, before `actions/cache` saves it, because GitHub rejects an entry over 10 GB; the cache is saved even when the build fails, so the next attempt starts from the work that did get through. The runner is cleaned first — every Xcode but the selected one and all simulator runtimes go — since GitHub's macOS runners have only 14 GB free and this build plus its cache does not fit beside them.

Once, from the Mac that holds the Apple material:

```sh
bun run ci-secrets [--p12 <path>]
```

`scripts/ci-secrets.ts` sets all ten repo secrets itself. Seven of the values already live on the box and it reads them over `pai ssh` (the `.env`, `build-system/paigram.json` and `~/pai/data/config.json` there, plus the box's own `/m/telegram/info` for the bot name); the App Store Connect key and the distribution certificate exist nowhere but that Mac, so it reads the key out of `~/.appstoreconnect/private_keys/` and exports the certificate from the login keychain — macOS asks for the login password before it releases a private key, and if more than one distribution identity is in there it asks which one. `security export` cannot be pointed at a single identity, so it exports the keychain's identities and separates the chosen certificate and its key out with openssl; `--p12 <path>` skips all of that and takes a `.p12` exported by hand from Keychain Access instead. Every value goes to `gh secret set` on stdin, so none of them reaches argv or shell history. It needs `gh` logged in with access to the repo, and checks that before it reads anything.

The secrets it sets, for setting them by hand under Settings → Secrets and variables → Actions:

| Secret | What |
| --- | --- |
| `ASC_KEY_ID` | App Store Connect API key id |
| `ASC_ISSUER_ID` | App Store Connect issuer id |
| `ASC_KEY_P8` | base64 of `AuthKey_<id>.p8` (`base64 -i AuthKey_<id>.p8`) |
| `TEAM_ID` | Apple Developer team id |
| `DIST_CERT_P12` | base64 of the Apple Distribution certificate **with its private key** — the same certificate `scripts/provision.ts` picks, which is the newest unexpired one on the account |
| `DIST_CERT_P12_PASSWORD` | the password that `.p12` was exported with |
| `TELEGRAM_API_ID` | `api_id` from my.telegram.org |
| `TELEGRAM_API_HASH` | `api_hash` from my.telegram.org |
| `PAI_BOX_URL` | the box the app talks to |
| `PAI_BOT_USERNAME` | the box's bot username, without the `@` (set so the build does not have to reach the box) |

`.github/workflows/build.yml` is upstream Telegram's CI — a full Bazel build with fake codesigning, producing an unsigned ipa on a GitHub release. It no longer runs on pushes to master: macOS runners bill at ten times the Linux rate and that ipa is of no use here, so it is `workflow_dispatch` only and the TestFlight workflow is the only build a push can start.
